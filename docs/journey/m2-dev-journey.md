## 二、实现缺陷

### 1. 内核从未接入产品路径（G14）

`DougongKernel` 有完整的生命周期、服务注册、调用租约、ALC 装卸，177 项测试全绿。
但核实发现：`Dougong.Agent` 源码对它**零引用**，`Dougong.Cli` 只在 csproj 里引用了工程，
源码同样不用。

CLI 的真实装配是 `new ToolDispatcher(...)` / `new LoopAgentRuntime(...)`——
内核的租约、代次绑定、排空在真实会话中从未生效过一次。

- **被发现的方式**：不是读文档发现的。文档把 P1 写成"部分，插件生态未成型（M3）"，
  这个描述把"没接线"说成了"生态没长大"。是 grep 全仓库才发现的
- **教训**：`design.md` 写的"一切皆插件"是设计意图，不是实现状态。两者的差距
  只能靠查代码确认
- **可写成**：文档写得越漂亮，越要验证它

### 2. ACP 入口完全不经过内核

修完 REPL 之后才发现：`--acp` 走的是 `AcpComposition.ComposeAsync`，
全程不碰内核。而 `-- parity` 套件存在的理由正是"两个入口能力必须一致"。

- **教训**：修一处时问"还有几个入口"
- **可写成**：两个入口，两倍的机会忘掉其中一个

### 3. 存储被宿主裸持有

`SessionComposition._store` 是字段。服务注册进内核了，宿主自己也留着一份，
替换后旧实例仍会被 `/history` 使用。

第一次修的探针只查 `SessionComposition`——删掉字段后探针通过，但缺陷转移到了
`ToolDispatcher._store`。**单点探针会把人引向错的地方**。

最终做法是 `IStoreAccessor`（Agent 层契约）+ `KernelStoreAccessor`（走租约）+
`FixedStoreAccessor`（显式不参与替换），从类型层面让"长期持有实例"不可表达。

### 4. 审批器与 dispatcher 也被裸持有（G15）

同样的模式，但更难修：审批是 dispatcher 每次调用都要发生的事，dispatcher 又被运行时持有，
两者互为编排者，没有"每次重新解析"的自然断点。

最终仍然做了：`IApproverAccessor` / `IDispatcherAccessor`。
`LoopAgentRuntime` 从主构造函数改为显式构造函数以承载两种注入方式。

### 5. 跨会话工作区互斥根本不成立（G9）

缺口登记簿写的是"等桌面宿主"。核实后发现它**现在就是坏的**：
`ToolResourceGate` 的锁表是实例字段，而每个会话各 `new` 一个
（CLI REPL 一次、ACP 每 session 一次）。同一工作区的两个会话各持一把互不相干的锁。

ACP 天然支持多会话，所以这不是理论问题。

- **教训**："等触发条件"的条目要定期复核触发条件是否**已经满足**
- **可写成**：登记簿上写"以后再说"，不代表现在没事

### 6. 两个只读调用也要排队（G5）

`read_file` 声明 `Serial`，于是两个读互相等待——它们不改任何东西。

加资源级读写键时踩了三个坑：
1. **不能用 `ReaderWriterLockSlim`**——它线程亲和，而租约跨 `await`
2. **写者必须显式等读者清零**——只占 `WriteGate` 不够，"读者已经在读"这件事看不见
3. **多资源要按键排序加锁**——否则两个工具以不同顺序请求同一组资源会死锁

### 7. 思考字段名硬编码在七处（G12）

Agent 层与 format 共七处直接读写 `reasoning_content`。接一家用 `reasoning` 的
provider 会**静默丢弃**思考内容——不报错，只是下一轮上下文少了东西；
若对方要求回传，则退化为 400 且错误信息不含字段名。

修法的关键在于识破：**跨层契约不该使用 provider 字段名**。
改成 `AgentPropertyKeys.Reasoning`（中性键）+ `WireCompat.ReasoningField`（方言开关），
翻译交给连接器。

### 8. 未知结果不带参数（G10）

缺口登记簿写的是"缺幂等键"。核实后发现真问题更基础：
`UnknownOutcome` 只有 `InvocationId` 和 `ToolId`，恢复时宿主连"当时要做什么"都不知道。

只有 id 和工具名的对账，不叫对账。已修：`ToolCallStarted` 记录含参数原文。

### 9. `StoreDurability` 声明了却没人读（G7）

枚举有三个值，实现显式返回一个。但核实发现它在**产品代码里零消费**——
只有定义处赋值和一处测试包装器转发，宿主从不读、从不展示。

声明没人看就等于没声明。补上：启动横幅展示等级、三档描述互不相同、
ACP 降级时说明"本次会话不会被保存"。

### 10. `LeasedDispatcher.Tools` 抛异常，主循环发不出工具声明

真实进程验证时 stderr 报 `NotSupportedException`。我原本认为"读工具列表也要租约"，
但 `Tools` 是每轮同步读取的属性，抛了就整轮失败。

改为激活期内经 `InvokeAsync` 取冻结描述符快照——描述符本身是 clone 副本，
不含实现对象，缓存它不违反"不捕获实现实例"。

### 11. 多余的 Kernel 工程引用，让"分层独立"看起来不成立

`Dougong.Agent.csproj` 从 M0 建仓起就引用 `Dougong.Kernel`，而源码从没用过。
移除后全量构建通过，`deps.json` 也不再含 Kernel。

- **教训**：说"零引用"之前该确认**引用图**，不是只 grep 源码

## 三、测试缺陷（测试本身在说谎）

### 12. "放弃枚举释放租约"的初版断言是假绿

只测了"停用够快"，但泵在 `InvokeAsync` 里用的是外部 token，
测试从没触发它——所以就算完全不取消也能过。

收紧为"运行时的循环本身必须收到取消"后，反证才真的失败。

### 13. 收紧后又连抓到两处测试自身缺陷

- async iterator 里写在 `yield return` **之后**的 `Register` 永远不会执行
  （客户端已 break，迭代器不再恢复）
- `Task.WhenAny(...) == task` 比较的是 `Task<Task>` 引用，永远为 false

这两个都让检查变成恒定通过或恒定失败。

### 14. `Task.Delay(100)` 不是同步，是时间假设

`KernelStateCommitTests` 用固定睡眠等后台读取器。全量并行时 100ms 不够，
报 `Collection: []`；单跑却通过，容易被当成噪声。

修法是轮询到条件成立。反证方式值得记：同样让读取器延迟 200ms 启动，
固定睡眠版本**确定性失败**，轮询版本**通过**。

### 15. 探针扫出 0 处"违规"，因为它什么也没查

`bare-hold` 初版只查已加载程序集，而启动时不一定会碰到全部产品程序集。
于是扫描静默返回 0 处持有——"通过"但什么也没查。

修完后扫出 45 条噪声（编译器生成的 async 状态机字段），排除后得到 8 条真实持有。

- **教训**：探针失效的样子和"确实没有违规"一模一样

### 16. 手工写记录测不出"运行时会不会写"

G10 的初版验收手工写 `ToolCallStarted` 记录，断言参数能读回。
但手工写的记录当然带参数——测的是"我能不能写对 JSON"。

反证时没能命中。改成走真实运行时（让 `ToolCallCompleted` 提交失败制造窗口）才有效。

### 17. 默认值改了，但检查测不出默认值

转正之后发现：`acp-path-uses-kernel` 显式设了 `DOUGONG_KERNEL=1`，
**默认值改没改它都通过**。

补了 `default-path-uses-kernel`（不设环境变量）和 `opt-out-restores-direct-path`
（开关必须真能退回，否则它不是开关）。

### 18. 特征化探针该怎么退场

G12 的探针最初断言"缺陷存在且确实静默"。缺陷修好后它按设计失败，
提示"缺陷已修，请更新文档"。

改成验证修复本身，三种情形：默认方言、覆盖方言、**方言隔离**
（防"两个字段都读"的假实现——那会让两种方言互相污染）。
这个演化过程写在代码注释里。

## 四、判断错误（AI 协作视角）

### 19. 把"接口约束"扩大成"不能持有对象"

用户问"为什么要用租约"，我在回答里写了：

> 按内核规则写，就不能 `new` 一个 runtime 存起来，必须每次通过 `InvokeAsync` 拿租约

这句是错的。`architecture.md` 约束的是**插件提供的服务实例**
（不得长期缓存 `TService`，否则停用后旧实例仍被调用），
**不是**"宿主不能持有任何对象"。宿主自己 `new` 的对象不受此约束。

正确说法：`new` 一个对象没问题；问题是**该对象本应由内核提供**时却绕开了服务注册。

- **教训**：引用约束时回到原文，不要凭记忆转述

### 20. 用元数据检查冒充"两个入口都接了"

`acp-composition-uses-kernel` 查的是"程序集里存在 `RegisterAsync` 调用"，
但 REPL 与 ACP 共享同一程序集——**分不清是谁调了**。

只有真起 `--acp` 进程才能验证。而 ACP 会话是**懒创建**的：
不发 `session/new` 就不会装配，第一次跑检查时误以为没接线。

### 21. 反证失败三次，每次原因都不同

| 反证 | 为什么没命中 |
|---|---|
| G14 移除接线 | 构建有错误，跑的是旧 DLL |
| G10 去参数 | 验收是手工记录，不经运行时 |
| G12 写死字段 | 需要端到端往返，只测解码器测不出 |

三次都不是"缺陷不存在"，而是**反证本身没打中**。

- **可写成**：反证失败先怀疑反证

### 22. 说"33 套件"说了一整天

最终复检时对照实际输出才发现：实际 31 套，`kernel-wiring` 是 10 项不是 9 项，
`kernel-process` 是 5 项不是 4 项。

后两处是加了检查但没更新计数。这类偏差不危险，但会腐蚀"文档附证据"的可信度——
**读者分不清哪些数字核对过、哪些是顺手写的**。

### 23. 设计限制的价值，一开始说得很虚

用户问"设计限制的价值如何"，我第一版回答是抽象的三条。

核实后发现实质问题：`StoreDurability` **零消费**——声明了没人读。
于是价值为零。

补上展示后，价值才具体：任何人改动等级，用户输出会变，问题会被发现。

- **可写成**：没有消费者的契约等于注释

## 五、与 dsh / Cordis 的对标发现

本轮做了一次一手对比（[kernel-vs-cordis.md](../kernel-vs-cordis.md)），
读的是 Cordis core 源码（v4.0.0-rc.12）与 dsh 架构文档。

| 维度 | Cordis | Dougong |
|---|---|---|
| 在途调用计数 | **无**（`grep inflight\|drain` 零命中） | 有 |
| 排空超时 | **无**（`setTimeout\|budget` 零命中） | 四阶段预算 + 隔离 |
| 变化传播 | epoch 让消费者自动重装 | 不自动重载（明确不做热更新） |
| 扩展点密度 | 20+ 机制、三段工具瀑布 | 只有唯一 dispatcher |
| 未知副作用 | 折叠成 tool error | `OutcomeUnknown` 第一类表达 |

最反直觉的结论：**我们的设计纸面更严谨，但工程上 Cordis 是活的、我们是死的**——
因为它每一行都在 dsh 每次启动时跑，而我们的内核在产品路径上零引用（缺陷 1）。

## 六、可用的文章角度

按"有没有戏剧性"排序：

1. **177 项测试全绿，而核心组件从未被使用**
   —— 内核查得越认真越容易漏掉"谁在用它"（缺陷 1）
2. **文档把"没接线"写成了"生态没长大"**
   —— 同一个事实的两种描述，一个指向 M3，一个指向现在（缺陷 1）
3. **修好一处，缺陷转移到下一处**
   —— 单点探针让"修好了"只是看起来修好了（缺陷 3）
4. **登记簿写"以后再说"，而它现在就是坏的**
   —— G9 不是未来问题（缺陷 5）
5. **反证失败，先怀疑反证**
   —— 三次不同的原因，没有一次是"缺陷不存在"（判断错误 21）
6. **探针通过，因为它什么都没查**
   —— 扫出 0 处的样子和"确实没有违规"一模一样（测试缺陷 15）
7. **手工写的数据测不出程序会不会写**
   —— 测的是"我能不能写对 JSON"（测试缺陷 16）
8. **约束的准确边界**
   —— "不能缓存实现实例"不等于"不能持有对象"（判断错误 19）
9. **契约没有消费者就等于注释**
   —— `StoreDurability` 的故事（判断错误 23）
10. **纸面更严谨 ≠ 工程更好**
    —— 和 Cordis 的对比（第五节）

避免的角度：把它写成"修了 8 个缺口"。真正有价值的是——
其中 5 个在核实之前，文档都说它们是**别的问题**。
