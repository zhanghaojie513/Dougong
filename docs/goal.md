# Dougong 的设计承诺

> **这份文档是什么**：Dougong 对外承诺的四条性质，以及明确的反目标。
> 它约束实现，也约束对外表述——**没有通过验证的能力不写进来**。
>
> **它不是什么**：不是设计（[design.md](design.md)）、不是架构（[architecture.md](architecture.md)）、
> 不是上手（[getting-started.md](getting-started.md)）。判定"某一片工作算不算完成"的
> 内部标准不在这里。

## 一、最终目的

**交付一个 .NET 原生的插件化 Agent Harness SDK：内核小而有完整生命周期，
运行能力由插件组合而成，宿主能安全地装卸、重启、替换其中的任何一环，
并且在崩溃、取消、超时与恶意/写错的插件面前仍能给出可解释的结果。**

参照 dsh 的架构思想，不移植其代码。

## 二、四条不可让渡的性质

下面四条是"最终目的"的可操作分解。它们不是并列的功能清单，而是**互相约束**的：
少任何一条，另三条都会失真。

### P1. 可组合（Composability）

运行能力（存储、审批器、工具、模型工厂、MCP 连接、REPL）能作为插件被组合进内核，
而不需要在宿主里永久缓存具体实现。

**不可让渡的部分**：只有现有扩展契约足够时，新能力才可以独立发布而无需修改内核。
需要修改内核才能接入的"可扩展"，不算可组合。

**这条约束的是"能力"，不是"事实"。**

- 要求内核换个**实现**（比如"运行时必须可替换"）→ 这是 P1 要守的
- 要求内核多**报告**一项它本就在测的东西（耗时、失败类别、展示字段）→ 正常演进，不算违反

一句话区分：**改的是"内核做什么"，还是"内核报告什么"？**

### P2. 有完整生命周期（Lifecycle Integrity）

注册、激活、停用、排空、清理、卸载各有明确语义与预算；任一阶段失败都不留
需要重启宿主才能清理的中间态（除非明确标记为隔离）。

**不可让渡的部分**：状态机里每个终态都可判定；没有"看起来成功"的路径。

### P3. 故障可解释（Explainable Failure）

崩溃、取消、超时、副作用结果未知时，系统能说清"哪些一定发生了、哪些一定没发生、
哪些不知道"，并且不自动重放不安全操作。

**不可让渡的部分**："不知道"必须能表达，不能与"没发生"混为一谈。

### P4. 真实可用（Actually Usable）

用真实 provider 跑真实任务时，协议层、工具管线与恢复语义都成立。

**不可让渡的部分**：只通过假模型验证的能力不算可用。假模型验证控制流，
真实 provider 验证协议与行为。

## 三、反目标（明确不做，做了就是跑偏）

以下方向明确不做。列出来不是谦虚，是防止"看起来相关就顺手加"。

| 反目标 | 为什么不做 |
|---|---|
| 做完整的 provider 矩阵（几十家厂商逐一对齐） | 方言差异已收口在 `WireCompat`，逐家适配是维护成本黑洞；标准协议够用 |
| 做通用工作流编排 / 可视化 DAG | 那是另一个产品；本项目的边界是"承托 Agent 运行" |
| 自建向量数据库 / 长期记忆基础设施 | L1 偏好记忆已足够；再往上做会让 SDK 绑定具体检索实现 |
| 模仿某个 CLI 的全部交互 | 参考宿主是示范，不是产品竞品 |
| 承诺跨大版本 API 稳定（当前 `0.x`） | 只承诺"变更被自动检出并记录"，见 [compat-policy.md](compat-policy.md) |
| 宣称未验证的能力 | P4 的直接推论：假模型验证控制流，不能冒充协议正确性 |

### 反目标的边界：什么不算"provider 矩阵"

第一行容易被读宽，所以把边界写清。

**"provider 矩阵"指的是逐家写适配代码**——每接一家就要改协议实现、处理它独有的
字段名与怪癖。那是维护成本黑洞，因为成本随厂商数量线性增长，而正确性依赖
逐家实测。

**端点地址表不算。** 内置预设每条只有三个字段：`base_url`、`wire_api`、
`key_env`（密钥**变量名**）。一行特例代码都没有——协议差异早就收敛在三种
wire format 与 `WireCompat` 里。加一家新预设不改任何代码，也不增加任何
需要验证的协议分支。

**列表要够用，但每条都得能验证。** 预设目前 19 条（国内 10、国际 6、聚合与本地 3）。
两个来自实践的要求：
- **够用**：只有 openai/anthropic/deepseek 三家时，国内可用的大模型
  （glm、kimi、mimo、minimax…）根本选不到，而列表的作用就是"选得到"。
- **能验证**：每条端点与密钥变量名都实测核对过（各端点返回 401/403/404
  而非 DNS 失败）。写了但连不上的条目比不写更糟——用户会以为是自己配错了。

这两条不冲突：加条目的成本是一行数据，验证成本是一次 curl。

**判据**：若某项改动只需要往数据表里加一行，它不是矩阵；若它需要为某家写
`if`、改字段映射、或加一个只有它用的开关，它就是矩阵，不做。
另有对照验证（`provider` 套件的 `presets-are-data-only`）钉住预设表的形状：
一旦有人往里加模型名或厂商特例字段，那条会先红；同时断言
glm / kimi / mimo / minimax 等必须存在，防止列表以后又被精简回去。

**为什么预设不带模型名**：同一端点的可用模型会变（新增、下线、改名）。
写死会让用户拿到一个 404 且看不出原因，而"模型名由用户给"永远不会过时。

## 四、四条性质怎样落到每一片工作

每一片交付都要能回答"它推动了哪一条性质"，并且不能损害其余三条。

一个具体的例子：加"推理内容实时事件"（`AgentEvent.ReasoningDelta`）——
- 它服务于 **P4 真实可用**：真实 provider 的思考模式以前拿不到实时流
- 它不能损害 **P2**：事件是新增的，不能改变任何既有生命周期语义
- 它不能损害 **P3**：推理内容若只进历史不产出事件，就是"看起来支持、实际拿不到"

更完整的门禁与自检方式属于内部流程，不在公开文档里。

代码注释会引用本文的性质编号（如 `goal.md` P3），因为它表达的是
