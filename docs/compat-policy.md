# 兼容策略

> **状态**：2026-10-26 制定。适用于 `0.1.0-alpha.1` 及之后的版本。
> **一句话**：`0.x` 不做向后兼容承诺，但**每一条公开 API 变更都会被自动检出并记录**。

---

## 一、承诺什么，不承诺什么

| | 承诺 | 不承诺 |
|---|---|---|
| 版本号 | 遵循语义化版本规则 | — |
| 公开 API 变更 | **自动检出**（`dotnet pack` 时） | 不保证旧代码能继续编译 |
| 变更记录 | 每条都进 CHANGELOG | 不保证给出迁移示例 |
| 弃用 | 先标 `[Obsolete]` 再删 | 不承诺弃用窗口的具体长度 |
| 可观察行为 | 破坏性变化记入 CHANGELOG | 不承诺行为完全不变 |

**"不承诺兼容"不等于"可以悄悄改"。** 这两件事经常被混为一谈：
前者是说用户要准备好改代码，后者是说用户根本不会知道。本策略禁止后者。

## 二、哪些包属于契约面

| 包 | 受 ApiCompat 保护 | 说明 |
|---|---|---|
| `Dougong.Kernel` | ✅ | 插件内核契约 |
| `Dougong.Agent` | ✅ | 执行层契约（dispatcher / runtime / 工具） |
| `Dougong.Ai` | ✅ | 三协议连接器与工厂 |
| `Dougong.Mcp` | ✅ | MCP 工具桥接 |
| `Dougong.Acp` | ✅ | ACP Agent 端 |
| `Dougong.Cli` | ❌ | 它是**工具**不是库（`PackAsTool`）。公开类型面向命令行用户，不是 API 消费者 |

`Dougong.Telemetry` 尚不存在（见 `README.md` 的能力表）。它出现时同样纳入。

**2026-10-26 的变化**：此前只有 Kernel 与 Agent 配了 `EnablePackageValidation`。
Ai / Mcp / Acp 三个包共 37 个公开类型**完全没有保护**，破坏性改动不会被发现。
现在五个包全部纳入，基线在 `artifacts/baseline/`。

## 三、什么算破坏性变更

ApiCompat 报 `CP****` 的都是。按影响分三档：

### 3.1 直接破坏（必须走弃用流程）

- 删除公开类型或成员
- 改方法签名（加/删/重排**必填**参数、改返回类型）
- 改类型名、命名空间
- 把 `public` 改小
- 给接口加新成员（实现方会编译失败）

### 3.2 行为破坏（ApiCompat 检不出，靠 CHANGELOG）

- 默认值改变（例如某个开关从"默认开"变"默认关"）
- 语义收窄（原本接受 `null`，现在抛异常）
- 输出格式变化（日志、事件字段、诊断文本）

**这一类最危险**：编译能过，运行时才出问题。所以：

> **凡是改变可观察行为的改动，必须在 CHANGELOG 里单独写一行，并说明
> "此前行为 → 现在行为"。** 只写"改进了错误提示"不算记录。

### 3.3 不算破坏

- 加新的公开类型/成员（接口成员除外）
- 加可选参数（有默认值）
- 放宽约束（原本抛异常，现在接受）
- 内部重构、私有成员变化

## 四、弃用流程

### 4.1 什么时候必须弃用而不是直接删

公开 API 上**已经有人可能依赖的**东西：直接删会让用户"编译突然失败且不知道原因"。
走弃用至少给一次版本的交界。

### 4.2 做法

```csharp
[Obsolete("用 NewThing 代替。此成员将在 0.3.0 移除。")]
public void OldThing() { ... }
```

三条要求：

1. **消息里写替代方案**，不能只写"已弃用"
2. **写预期移除的版本号**，不写"以后"
3. **保留至少一个次版本**（`0.1.x` 标弃用 → 最早 `0.2.0` 才删）

### 4.3 弃用窗口的长度

`0.x` 阶段：**至少一个次版本**（minor）。

理由：`0.x` 阶段版本推进可能很快，承诺"半年"没有意义；但"下一个 minor"是可验证的，
而且足够让用户在升级时看到编译警告。

到 `1.0` 之后改为主版本窗口（`1.x` 标弃用 → `2.0.0` 才删）。

### 4.4 删除时

1. 先在 CHANGELOG 的 `Removed` 段写明删了什么、替代是什么
2. 跑 `scripts/update-api-baseline.sh` 更新基线
3. 确认 `dotnet pack` 通过（此时基线已包含这次删除）

## 五、实验性边界

**本项目当前没有任何 `[Experimental]` 标记**，也不打算加。

理由（2026-10-25 决策）：`[Experimental]` 在 C# 里产生的是 **error 而非 warning**，
调用方不加 `NoWarn` 就构建失败。对第三方插件作者来说，这个代价远大于
"知道某 API 不稳定"的收益。改用 ApiCompat + CHANGELOG 让变更可见。

所以本项目的态度是：

| 状态 | 怎么表达 |
|---|---|
| 稳定 | 不加任何标记 |
| 打算改 | CHANGELOG 里 `Changed`/`Deprecated` |
| 要删 | `[Obsolete]` + 至少一个次版本 |

**没有"实验性所以怎么改都行"这一类。** 所有公开 API 都按本文的规则走。

## 六、版本号规则

遵循语义化版本，但在 `0.x` 阶段有一条重要调整：

| 变更 | `0.x` 阶段 | `1.0` 之后 |
|---|---|---|
| 破坏性变更 | **minor +1**（`0.1.0` → `0.2.0`） | major +1 |
| 新增功能 | patch +1 | minor +1 |
| 修 bug | patch +1 | patch +1 |

`0.x` 阶段把破坏性变更放 minor 是 semver 的规定（`0.x` 的 minor 视为"任意"）。
但本项目额外要求：**minor 里出现破坏性变更时，CHANGELOG 必须在最上面显式警告**。

版本号唯一来源是 `Directory.Build.props` 的 `<Version>`。
（`Program.cs` 里还有两处硬编码的版本字符串，那是显示用的，改版本时要一起改——
这是已知的重复，见 §七。）

## 七、已知的不完善

如实列出，不假装这套机制是完整的：

1. **`Program.cs` 里版本号硬编码了两处**，与 `Directory.Build.props` 重复。
   改版本时容易漏。`--report` 用的是程序集版本（真实值），不受影响。
2. **行为破坏靠人工判断**。ApiCompat 只看签名，语义变化只能靠写 CHANGELOG 的人自觉。
   没有自动化手段能检出"默认值变了"。
3. **`0.x` 阶段实际没有外部用户**，所以这套流程还没有被真实升级场景检验过。
   它的价值现在主要是"防止我们自己悄悄改坏"，而不是"保护已有用户"。
4. **没有迁移指南**。弃用时给的是替代方案名，不是完整迁移步骤。

### 7.1 配置迁移与回滚：判定为"现在不做"，附触发条件

I0 的交付清单里有一项"安装与升级：配置迁移与回滚"。核查后的判定是**暂不实现**，
理由不是"忘了"，而是当前没有可迁移的对象：

| 事实 | 来源 |
|---|---|
| 配置只有环境变量（`DOUGONG_*`），没有配置文件格式 | `Doctor.cs` / `SessionComposition.cs` 实测 |
| 环境变量没有版本号，也没有"旧名字 → 新名字"的历史 | 同上 |
| 会话与记忆是 append-only JSONL，格式未被标记版本 | `JsonlAgentStore.cs` / `MemoryStore.cs` |
| 外部用户数为 0 | 仓库私有，见 `status.md`「仓库可见性」 |

**"迁移"要解决的是"旧数据在新版本里读不出来"。** 目前不存在旧数据，
所以现在写迁移工具只会是凭空造一个从没发生过的场景。

**什么时候该做**（任一成立）：

- 首次出现**磁盘持久化格式**变更（JSONL 字段增删、目录布局调整）
- 首次**重命名或删除** `DOUGONG_*` 环境变量
- 出现第一个报告"升级后打不开旧会话"的用户

**回滚**同理：`dotnet tool uninstall` + 重装旧版本即可，包本身不自带状态。
只有当日志格式发生不兼容变更时，才需要"降级也能读"的保证。

这一条与 §七 的第 4 点（没有迁移指南）是同一个判断的两面：
**弃用流程里的"替代方案名"够用，是因为还没有人真的需要搬运旧配置。**

## 八、这套策略怎么被验证

不是写完就算。以下每条都有对应的检查或脚本：

| 机制 | 怎么验证 |
|---|---|
| ApiCompat 覆盖五个包 | `-- apicompat` 检查项：五份基线存在，且破坏性变更能被检出 |
| 冒烟验证真实有效 | 同一检查项里插入一个真实的破坏性变更，断言 `CP0002` 出现 |
| 基线不腐化 | `all-checks.sh` 在 pack 阶段执行 ApiCompat；CI 断言基线文件存在 |
| 变更被记录 | 人工约定（见 `quality-gates.md`），无自动化 |

前三条进 CI。第四条明确说明是人工的——不假装它被自动保证了。
