## 零、结论（先说结果）

**在 14 个真实组合上，启用记忆后偏好遵循率从 0–10% 提升到 70–100%，提升幅度 60%–90%，中位数 80%。14/14 全部超过预先登记的 50% 阈值。**

| 组合 | 有记忆 | 无记忆 | 提升 |
|---|---|---|---|
| bigmodel / GLM-5.3 / openai | 100% | 10% | +90% |
| bigmodel / GLM-5.3 / anthropic | 90% | 10% | +80% |
| bigmodel / GLM-5.3-Flash / openai | 100% | 10% | +90% |
| bigmodel / GLM-5.3-Flash / anthropic | 100% | 10% | +90% |
| deepseek / deepseek-flash / openai | 90% | 0% | +90% |
| deepseek / deepseek-flash / anthropic | 70% | 10% | +60% |
| xiaomi / mimo-v2.6-flash / openai | 100% | 10% | +90% |

| waygate / deepseek-v4.1-flash / openai | 90% | 10% | +80% |

**这个结论的适用范围**：被测的这 6 家模型、这 10 个任务、这两种偏好
（`output.format=concise` 与 `naming.convention=PascalCase`）。
**不外推到**其它模型、其它偏好、其它任务类型。

## 一、这一项要回答什么

前面 2–6 条验收回答的是"记忆管道安不安全"：能不能被篡改、能不能撤销、会不会重复启用。
全部通过。

**它们都没有回答"记忆有没有用"。**

验收 1 要回答的就是这个：**在留出任务上，启用记忆后模型是否更倾向于遵守用户此前的偏好。**

这两件事必须分开说。管道安全 + 效果未知 ≠ 记忆功能可用。
把前者说成后者，就是本项目一直在防的那类"假通过"。

## 二、装置怎么做的

### 2.1 两组对照

| 组 | 配了什么 | 期望 |
|---|---|---|
| 有记忆 | `LoopAgentRuntime.Memory = StoreMemoryInjector(store)` | 遵守偏好 |
| 无记忆 | `Memory = null` | 大概率不遵守 |

两组用**同一个模型、同一批任务、同一个提示**。唯一差别是注入器。

### 2.2 十个留出任务（v2）

两类偏好，各 5 个任务，全部是**中性请求**——提示里不提任何偏好：

| 键 | 任务举例 | 提示原文 | 判据类型 |
|---|---|---|---|
| `output.format=concise` | explain-http-cache | `说明 HTTP 缓存的工作方式。` | **相对** |
| `naming.convention=PascalCase` | name-config-fields | `为一个配置对象起三个字段名并说明用途。` | 绝对 |

**提示为什么必须中性**：一旦写了"请简短回答"，两组都会照做，提升幅度变 0，
而我们可能误判成"记忆没用"。有专门检查项 `prompt-does-not-leak-preference` 守着。

### 2.3 判据机械化，不用裁判模型

**concise 用相对判据**：有记忆组的回答必须比无记忆组**短至少 15%**。

为什么不用绝对阈值：一开始定的是"≤200 字符"，实测发现模型收到 concise 偏好后
压到 207–813 字符（默认 893–1243）。它确实照做了，只是"多短算短"没有客观标准——
200 是凭感觉定的，与模型行为不匹配。用绝对阈值会把"部分遵循"记成"完全没遵循"。

为什么要求 15% 的降幅而不是"只要更短"：同一模型两次调用之间长度本来就有波动，
不设最小幅度会把噪声当效果。下限 40 字符排除"只回一句好"的退化。

**PascalCase 用绝对判据**：PascalCase 标识符**至少 2 个**且**多于** camelCase。

为什么要"至少 2 个"：实测发现无记忆组的回答里偶尔出现单个 PascalCase
标识符（例如订单表的 `OrderId`——那是业界惯例，不是响应偏好）。
只要求"出现一个"会把偶然命中记成遵循，抬高无记忆组基线、低估效果。
这条缺陷是跑完 v2 第一轮后从逐任务表里发现的。

**不用第二个模型当裁判**的原因：那会把"记忆有没有用"变成"裁判准不准"，
而且每次评估都要多花一次调用。

### 2.4 预先登记的阈值

```csharp
public const double RequiredLift = 0.5;
```

10 个任务里，有记忆组必须**至少多遵守 5 个**。

定这么高的理由：偏好遵循是容易的行为——模型只是不知道用户偏好，知道就会做。
如果提升只有 1–2 个，说明注入没生效或模型忽略了注入，两种情况都不该算"记忆有用"。

**这个数字是跑之前写进代码的，不是跑完看结果再定的。** 达不到就是达不到，
回头改阈值等于自欺。

## 三、怎么跑

```bash
bash scripts/run-l1-effect.sh
```

脚本会：
1. 检查 `DOUGONG_PROVIDER_BASE` / `MODEL` / `KEY`，缺失的交互式提示输入（`read -s`，不回显）
2. 显示会产生的调用次数（20 次 = 10 任务 × 2 组）并要求确认
3. 构建并运行

密钥只在进程内存在，不写任何文件——这从 M1 起就是硬规则
（见 [m1-candidate-comparison.md](m1-candidate-comparison.md)）。

没有凭证时运行 `-- l1-effect` 会输出：

```
L1-EFFECT: 未运行（缺少 DOUGONG_PROVIDER_BASE / KEY / MODEL）。
  这不是通过。
```

**返回码 2，不是 0**，所以脚本和 CI 都不会把它当成功。

## 四、装置本身被验证过

装置自检 `-- l1-harness` 用行为确定的假模型验证"尺子准不准"，
不需要真实模型，已进 `all-checks.sh`：

| 检查项 | 验证什么 |
|---|---|
| `criteria-accept-following` | 明显遵循的回答被判为遵循 |
| `criteria-reject-non-following` | 明显不遵循的回答被判为未遵循 |
| `criteria-tolerate-alternative-shapes` | 15% 降幅边界、对照组为空等边界行为正确 |
| `memory-reaches-the-model` | 有记忆组：模型确实收到了偏好段落 |
| `no-memory-group-sees-nothing` | 无记忆组：即使存储里有偏好，模型也看不到 |
| `prompt-does-not-leak-preference` | 10 个任务的提示都不含偏好线索 |

**7 条反证全部如期变红**（`scripts/l1-harness-counterproofs.sh`）：
把判据写宽、写窄、去掉比较那一半、让对照组也拿到注入器、往提示里塞偏好——
每一种都能让对应检查失败。

### 自检与实跑中发现并修掉的四个真实缺陷

1. **`naming` 判据里有死代码**：原写法 `HasSnakeCase(t) && !HasCamelCase(t)`，
   后半句被前半句蕴含。反证时该改动完全不生效才暴露。改成计数比较。
2. **只有反例、没有中间态**：删掉"snake > camel"这一半时检查仍全绿，
   因为反例里 snake 计数是 0。补了中间态用例后这一半才真正被测到。
3. **concise 的绝对阈值（200 字符）与模型行为不匹配**：实测注入后 207–813 字符。
   模型确实照做了，只是"多短算短"没有客观标准。改成相对判据（比无记忆组短 15%）。
4. **单个 PascalCase 标识符被算作遵循**：无记忆组回答里的 `OrderId`
   是业界惯例的偶然命中，被判成遵循，抬高基线、低估效果。
   加上"至少 2 个"下限后修正。

## 五、怎么解释结果

跑出来的数字只有四种情况，各有明确含义：

| 结果 | 说明 | 下一步 |
|---|---|---|
| 提升 ≥ 50% | 记忆在本条件下有效 | 可以声明"在该模型与该任务集上有效"，**不外推** |
| 提升 10–50% | 有效但不稳定 | 查是哪一类任务没跟上（逐任务表会显示） |
| 提升 ≈ 0 | 注入没生效，或模型忽略注入 | 先查 `memory-reaches-the-model`，再看 system 消息的实际内容 |
| 提升为负 | 有无记忆组反而更差 | 警示信号，注入内容干扰了模型，必须查清再继续 |

**本次实测落在第一档**（+60%～+90%）。

**无论结果如何，结论的适用范围只有：被测模型 + 这 10 个任务 + 这一次运行。**
不进 `status.md` 的"已实现"栏，只进"验收证据"栏并注明条件。

## 六、这一项仍然不能证明什么

即使跑出 100% 提升，也**不能**证明：

- 换一个模型还有效
- 换成别的偏好还有效
- 长期使用会越来越好（这是 L2+ 的问题，需要"生成候选"那一整片工作）
- 用户会满意（满意度不是遵循率）

它只证明一件事：**在当前注入实现下，模型确实会依据注入的偏好改变输出。**

这个结论很小，但它是真的。而"记忆系统很有用"这个大结论，
需要的证据比这多得多。

## 七、v1 基线（保留，不废弃）

v1 用 4 个 `language=中文`、3 个 `output.format=bullets`、3 个 `naming.convention=snake_case`
任务，在同样 14 个组合上跑出：

| | 有记忆 | 无记忆 | 提升 |
|---|---|---|---|
| v1 全部 14 个组合 | 100%（14/14 组合都是 10/10） | 70%–90% | +10% ~ +30%，中位数 +20% |

**v1 证明了什么**：注入在 6 家 provider × 2 种协议上**一致生效**——
有记忆组在全部 14 个组合里都是 100%。这是真实且重要的结论。

**v1 测不出什么**：提升幅度。`language=中文` 那 4 个任务两组都是 4/4
（这些模型默认就用中文），零区分力，把理论最大值压到 60%。
所以 v1 的"未达 50% 阈值"不是"记忆无效"，而是**任务集没有区分力**。

**这就是为什么有 v2**：v2 只测"模型默认不会做"的偏好
（concise 压制长篇倾向、PascalCase 反命名直觉）。
v2 的 +60%～+90% 才是记忆效果的真实幅度。

两批结果分开记录，**不混报**——把 v2 的数字套在 v1 任务集上，
或者用 v2 的结论去说 v1 的"通过"，都是错的。
