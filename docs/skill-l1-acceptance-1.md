## 一、这一项要回答什么

前面 2–6 条验收回答的是"记忆管道安不安全"：能不能被篡改、能不能撤销、会不会重复启用。
全部通过。

**它们都没有回答"记忆有没有用"。**

验收 1 要回答的就是这个：**在留出任务上，启用记忆后模型是否更倾向于遵守用户此前的偏好。**

这两件事必须分开说。管道安全 + 效果未知 ≠ 记忆功能可用。
把前者说成后者，就是本项目一直在防的那类"假通过"。

## 二、装置怎么做的

### 2.1 两组对照

| 组 | 配了什么 | 期望 |
|---|---|---|
| 有记忆 | `LoopAgentRuntime.Memory = StoreMemoryInjector(store)` | 遵守偏好 |
| 无记忆 | `Memory = null` | 大概率不遵守 |

两组用**同一个模型、同一批任务、同一个提示**。唯一差别是注入器。

### 2.2 十个留出任务

三个白名单键各 3–4 个任务，全部是**中性请求**——提示里不提任何偏好：

| 键 | 任务举例 | 提示原文 |
|---|---|---|
| `language=中文` | explain-http-cache | `简要说明 HTTP 缓存的工作方式。` |
| `output.format=bullets` | list-review-tips | `列出三条代码评审建议。` |
| `naming.convention=snake_case` | name-config-fields | `为一个配置对象起三个字段名并说明用途。` |

**提示为什么必须中性**：一旦写了"请用中文回答"，两组都会照做，提升幅度变 0，
而我们可能误判成"记忆没用"。这是整个实验最容易出错的地方，
所以有一条专门的检查项 `prompt-does-not-leak-preference` 守着它。

### 2.3 判据机械化，不用裁判模型

| 键 | 判据 | 为什么可靠 |
|---|---|---|
| `language` | 回答里是否含 CJK 字符（U+4E00–U+9FFF） | 字符集可数，不涉及语义 |
| `output.format` | 是否有 ≥2 行以 `-`/`*`/`•`/`1.` 开头 | 只查形状 |
| `naming.convention` | snake_case 标识符是否多于 camelCase 标识符 | 计数比较，不判命名好坏 |

**不用第二个模型当裁判**的原因：那会把"记忆有没有用"变成"裁判准不准"，
而且每次评估都要多花一次调用。

`naming` 的判据是"snake 多于 camel"而不是"全是 snake"：模型偶尔漏一个字段写成
camelCase，仍是响应了偏好，只是不完美。用"全对"当标准会低估效果。

### 2.4 预先登记的阈值

```csharp
public const double RequiredLift = 0.5;
```

10 个任务里，有记忆组必须**至少多遵守 5 个**。

定这么高的理由：偏好遵循是容易的行为——模型只是不知道用户偏好，知道就会做。
如果提升只有 1–2 个，说明注入没生效或模型忽略了注入，两种情况都不该算"记忆有用"。

**这个数字是跑之前写进代码的，不是跑完看结果再定的。** 达不到就是达不到，
回头改阈值等于自欺。

## 三、怎么跑

```bash
bash scripts/run-l1-effect.sh
```

脚本会：
1. 检查 `DOUGONG_PROVIDER_BASE` / `MODEL` / `KEY`，缺失的交互式提示输入（`read -s`，不回显）
2. 显示会产生的调用次数（20 次 = 10 任务 × 2 组）并要求确认
3. 构建并运行

密钥只在进程内存在，不写任何文件——这从 M1 起就是硬规则
（见 [m1-candidate-comparison.md](m1-candidate-comparison.md)）。

没有凭证时运行 `-- l1-effect` 会输出：

```
L1-EFFECT: 未运行（缺少 DOUGONG_PROVIDER_BASE / KEY / MODEL）。
  这不是通过。
```

**返回码 2，不是 0**，所以脚本和 CI 都不会把它当成功。

## 四、装置本身被验证过（但没有效果结论）

真实模型跑不了的时候，装置仍然可以自检。`-- l1-harness` 用行为确定的假模型
验证"尺子准不准"：

| 检查项 | 验证什么 |
|---|---|
| `criteria-accept-following` | 明显遵循的回答被判为遵循 |
| `criteria-reject-non-following` | 明显不遵循的回答被判为未遵循 |
| `criteria-tolerate-alternative-shapes` | `*`/`•`/`1.` 等其它列表写法也接受，但仍拒绝段落 |
| `memory-reaches-the-model` | 有记忆组：模型确实收到了偏好段落 |
| `no-memory-group-sees-nothing` | 无记忆组：即使存储里有偏好，模型也看不到 |
| `prompt-does-not-leak-preference` | 10 个任务的提示都不含偏好线索 |

**6 条反证全部如期变红**（`scripts/l1-harness-counterproofs.sh`）：
把判据写宽、写窄、让对照组也拿到注入器、往提示里塞偏好——每一种都能让对应检查失败。

### 自检过程中发现并修掉的两个真实缺陷

1. **`naming` 判据里有死代码**：原写法 `HasSnakeCase(t) && !HasCamelCase(t)`，
   后半句被前半句蕴含（纯 camelCase 文本没有下划线，本来就不满足 `HasSnakeCase`）。
   反证时该改动完全不生效才暴露。改成计数比较后两个方向都有意义。
2. **只有反例、没有中间态**：删掉"snake > camel"这一半时检查仍然全绿，
   因为反例里 snake 计数是 0，`snake > 0` 已经拒绝了。补了"以 camelCase 为主、
   混入一个 snake_case"的中间态用例后，这一半才真正被测到。

## 五、怎么解释结果

跑出来的数字只有四种情况，各有明确含义：

| 结果 | 说明 | 下一步 |
|---|---|---|
| 提升 ≥ 50% | 记忆在本条件下有效 | 可以声明"在该模型与该任务集上有效"，**不外推** |
| 提升 10–50% | 有效但不稳定 | 查是哪一类任务没跟上（逐任务表会显示），别急着宣称成功 |
| 提升 ≈ 0 | 注入没生效，或模型忽略注入 | 先查 `memory-reaches-the-model`，再看 system 消息的实际内容 |
| 提升为负 | 有无记忆组反而更差 | 这是警示信号，说明注入内容干扰了模型，必须查清再继续 |

**无论结果如何，结论的适用范围只有：被测模型 + 这 10 个任务 + 这一次运行。**
不进 `status.md` 的"已实现"栏，只进"验收证据"栏并注明条件。

## 六、这一项仍然不能证明什么

即使跑出 100% 提升，也**不能**证明：

- 换一个模型还有效
- 换成别的偏好还有效
- 长期使用会越来越好（这是 L2+ 的问题，需要"生成候选"那一整片工作）
- 用户会满意（满意度不是遵循率）

它只证明一件事：**在当前注入实现下，模型确实会依据注入的偏好改变输出。**

这个结论很小，但它是真的。而"记忆系统很有用"这个大结论，
需要的证据比这多得多。
