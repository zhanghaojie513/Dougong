# M3 计划：把能力变成别人能用的产品

> **状态**：计划（2026-10-25），未开始。等用户指令启动。
> **上游依据**：`goal.md` §五（M3 = P1 的生态部分）、`design.md` §九（M3 判据）、
> `quality-gates.md`（六道门）、`vision/iteration-roadmap.md` I0。
> **M3 的一句话目标**：一位没参与开发的人，能照着文档写出一个可信插件、跑起来、
> 并知道它什么时候会失败。

---

## 一、M3 到底要解决什么

先厘清三个常被混为一谈的东西：

| | 已在 M0–M2 完成 | M3 要做 |
|---|---|---|
| **能力** | 内核装卸、租约排空、工具管线、三协议、MCP/ACP | 不新增 |
| **可替换性** | 四种能力有替换实测（存储/客户端/审批器/dispatcher/运行时） | 不新增 |
| **可用性** | 我们**自己**能跑（CLI + 测试） | **别人**能跑 |

所以 M3 不是加功能，是**把已有能力封成一个别人不会用错的形状**。

**判据来自 `goal.md` P1**：「只有现有扩展契约足够时，新能力才可以独立发布而无需修改内核」。
M0–M2 证明了"我们可以替换"，M3 要证明"**别人可以替换且不需要读我们的源码**"。

## 二、当前真实差距（实测，不是估计）

| 项 | 现状 | 差距性质 |
|---|---|---|
| `Experimental` 标记 | **0 处**。而 `design.md:249` 与 M3 定义都写"公共 API 在 M3 前保持 experimental" | **未兑现的承诺**——要么补标记，要么改文档说明为何不标 |
| ApiCompat / 包校验 | **无**。csproj 里没有任何 `PackageValidation` 或 `ApiCompat` 配置 | 无法在改 API 时自动发现破坏 |
| 公开 API 面 | 133 个公开类型（Kernel 24 / Agent 71 / Ai 15 / Mcp 10 / Acp 13） | 数量本身不是问题，问题是**哪些该稳定** |
| 多轮卸载测试 | 7 项（`KernelDynamicLoadingTests`），含 `WeakReference` + 强制 GC | 有基础，但未覆盖"多轮装卸后仍不泄漏" |
| 插件作者文档 | `samples/README.md` 有 4 个 M0 样例；M1/M2 样例标着"规划" | **M1/M2 样例不存在**；没有"从零写一个插件"的指南 |
| 装配可配置性 | `ConnectMcpAsync` 硬编码两种传输构造 | 第三方加传输要改装配代码（见 §六 待办 1） |
| 性能基线 | 无实测数字 | `iteration-roadmap.md` I0 要求"写进文档而非宣称" |

**最重要的发现**：`Experimental` 标记是 0。这意味着要么我们的 API 已经在事实上被当作稳定面
（但没有承诺），要么文档写了一条从未执行的纪律。**这两者都必须选一个**，不能悬着。

## 三、M3 的完成判据（可执行）

M3 不是"做完清单"，是达到下面四条。每条都有明确的反例。

### 判据 1：外部作者能写插件，且不需要读我们的源码

**做法**：找一个没参与开发的人（或在不看源码的条件下，只读文档），完成：
安装 → 配置模型 → 跑一个真实任务 → **写一个工具插件并装上**。

**反例**：需要看 `Dougong.Agent` 源码才知道 `IAgentTool.DescribePermission` 该怎么填。
**反例**：需要猜 `ToolExecutionPlan` 的 `Reads`/`Writes` 该写什么格式。

> 这一条与 `iteration-roadmap.md` I0 的退出条件一致。它是 M3 的核心，
> 其他三条都是为了让这条成立。

### 判据 2：API 变更会被自动发现

**做法**：开启 `PackageValidation`（`EnablePackageValidation`）+ 基线包比对；
对 `Dougong.Kernel` 与 `Dougong.Agent` 两个最可能被第三方依赖的包启用 ApiCompat。

**反例**：删掉一个公开方法，`dotnet pack` 仍然成功。
**反例**：改了 `ToolDescriptor` 的构造参数顺序，测试全绿（因为测试和实现一起改了）。

### 判据 3：多轮装卸不泄漏

**做法**：现有 7 项卸载测试扩展到"同一插件反复装卸 N 轮（≥10）后，ALC 全部可回收、
服务表与事件订阅无残留"。断言用 `WeakReference` + 强制 GC，与现有做法一致。

**反例**：装卸 10 轮后某个 `WeakReference.IsAlive` 仍为 true。
**反例**：服务表里残留已卸载代次的条目。

### 判据 4：失败可定位到组件

**做法**：构造五类故障（插件激活失败、清理超时进隔离、服务缺失、ALC 卸载失败、
MCP 连接失败），每种都要输出"哪个插件、哪个阶段、下一步该做什么"。

**反例**：插件加载失败只报一个 `TargetInvocationException`，看不出是缺共享契约还是缺依赖。

## 四、切片顺序

按"哪一项最能暴露其他问题"排序，不按文档章节。

| 顺序 | 切片 | 为什么在这个位置 |
|---|---|---|
| 3.1 | **`Experimental` 标记补齐或明确放弃** | 这是纪律问题不是功能问题。先定，因为它决定了 3.2 的语义——标了 experimental 的 API 不进 ApiCompat 基线 |
| 3.2 | **ApiCompat + 包校验** | 一旦有基线，后续所有改动都会被自动检查。早做收益最大 |
| 3.3 | **多轮装卸不泄漏** | 这是"能不能装"到"能不能反复装"的差别，也是第三方最可能踩的坑 |
| 3.4 | **故障诊断五类** | 判据 4。它会让 3.1–3.3 的问题在测试中显形 |
| 3.5 | **作者文档 + M1/M2 样例** | 判据 1。放最后是因为前四项会改变 API 与诊断文本，文档要跟着改 |
| 3.6 | **装配可配置性（MCP 传输注入）** | 见 §六。低成本，放最后做不影响主线 |
| 3.7 | **性能基线实测** | 写进文档的数字，不是宣称。放最后是因为它不改变代码 |

**明确不做**（`iteration-roadmap.md` I0 也这么写）：新协议、新存储后端、新 agent 能力、
插件市场、桌面 UI。

## 五、3.1 必须先回答的问题：`Experimental` 标还是不标

这是 M3 第一个决策点，我不替你定，先把两种选择的后果说清。

**选项 A：补标记。** 给 133 个公开类型里"面向插件作者"的那些加 `[Experimental("DOUGONG001")]`。
- 好处：兑现 `design.md:249` 的承诺；作者会在编译期看到"这可能变"
- 代价：**每个使用者都要 `#pragma` 或项目级 suppress**，否则构建失败。而我们现在自己就有
  6 个项目、32 个套件在用这些 API——全都要加 suppress，噪声很大
- 风险：如果一个项目所有 API 都 experimental，等于没有标记

**选项 B：明确不标，改文档。** 承认 `design.md:249` 那条从未执行，改为
"API 在 1.0 之前不做兼容承诺，但通过 ApiCompat 跟踪变化并在 CHANGELOG 记录"。
- 好处：诚实；避免全项目 suppress 的噪声
- 代价：作者没有编译期警告，得靠文档和 CHANGELOG

**我的倾向：A 的收窄版** —— 只给**明确的插件作者面**加标记，不给全部。
具体是：`IPlugin`、`PluginContext`、`PluginManifest`、`ServiceRequirement`、
`IAgentTool`、`ToolDescriptor`、`ToolPermission`、`ToolExecutionPlan`、`AgentToolResult`。
理由：这些是第三方真正会实现的接口，其余（如 `JsonlAgentStore`、`LoopAgentRuntime`）是
我们的参考实现，作者不继承它们。

这个判断需要你确认，因为它影响所有使用者的构建体验。

## 六、待办登记（来自 M2 复盘的遗留判断）

| # | 项 | 定性 | 触发条件 |
|---|---|---|---|
| 1 | `ConnectMcpAsync` 的传输构造应可注入 | **不是缺接缝**——官方 SDK 的 `IClientTransport` 已是接缝，缺的是装配层的注入点（约 10 行） | 第三方需要 stdio/HTTP 之外的传输 |
| 2 | `McpServerSpec` 用 `Uri?` + `string? Command` 表达形态，无法容纳第四种 | 形态表达需要重构（枚举 + 各自参数） | 与 #1 同时 |
| 3 | 协议内方言只覆盖 `ReasoningField` / `MaxTokensField` | `WireCompat` 的开关是"已知踩过"的，不是完整矩阵 | 出现新的真实方言差异 |

这三条都不阻断 M3，但**如果做 3.6，应该连 #2 一起做**——否则注入点加了，
`McpServerSpec` 仍然表达不了新形态。

## 七、M3 的风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **文档写好了但没人验证** | 判据 1 要求"外部人不看源码能完成"，我们自己测不出来——我们已经知道答案 | 找真人试；或至少按"只读文档"的方式做一遍并记录卡住的地方 |
| **ApiCompat 基线一开始就有大量噪声** | 首次启用会把现有 133 个类型全部当基线，之后任何改动都报 | 先在 `Kernel` 一个包上试，确认噪声可接受再推广 |
| **多轮装卸测试在 CI 上不稳定** | `WeakReference` + `GC.Collect` 本身有不确定性 | 现有测试已经这么做（7 项），先沿用；如果 flaky 就加"重试上限 + 失败时报出存活引用类型" |
| **把 M3 做成"补文档"** | 最可能的失败模式：文档写得很全，但判据 1 那条从未真实验证 | 判据 1 是唯一的验收出口，其余三条是它的支撑 |

## 八、和 M4+ 的边界

`iteration-roadmap.md` 定义了 I1–I6（可嵌入运行时、执行边界、知识资产化、可度量进化、
互操作、产品面扩张）。**M3 不启动其中任何一项**，即使它们看起来更"有价值"。

M3 只做一件事：让现有能力变成别人能用的产品。M4+ 的内容等 M3 的判据 1 成立后再谈。
