# 性能基线

> **这份文档只记录数字，不做性能承诺。**
> `iteration-roadmap.md` I0 要求"把实测数字写进文档，而非宣称"——
> 数字会随硬件、SDK、数据形状变化，承诺会变成无法兑现的债。
>
> **怎么复现**：`dotnet run --project spike/Dougong.Agent.Comparison -c Release -- perf`
> 这个套件只输出数字，不参与通过/失败判定，因此不在 `scripts/all-checks.sh` 里。

## 测量环境（2026-10-28 复测）

| 项 | 值 |
|---|---|
| OS | Windows NT 10.0.26200.0 |
| CPU | 16 核 |
| .NET SDK | 10.0.402（运行时 10.0.13） |
| 配置 | Release，`--no-build` |

**换一台机器数字会变。** 这些数字的意义是"同机对比与趋势"，不是"绝对性能"。

**噪声**：`Flush(flushToDisk: true)` 受磁盘状态影响明显。2026-10-28 连测三次，
"追加 1000 条"在 0.87–4.62 ms/条之间波动。**读这组数字要看数量级，不要比小数点。**
其余各项（token 估算、插件装卸、并发）三次波动在 ±15% 内，可以直接比。

## 一、大会话（1000 条历史）

每条约 220 字节（一个 index + 200 字符文本），追加后重新打开并全量重放。

| 项 | 实测 |
|---|---|
| 打开会话文件 | 13 ms |
| 追加 1000 条 | 716 ms（0.72 ms/条） |
| 重放 1000 条 | 22 ms（0.02 ms/条） |
| 文件大小 | 263 KB |

**怎么读这组数字**

- **追加是重放的 33 倍**，符合预期：每次追加都做 `Flush(flushToDisk: true)`，
  这是提交屏障的成本，不是缺陷。想更快就得放弃落盘保证——那是另一个取舍。
- 0.72 ms/条意味着**一次工具调用的持久化开销远小于一次模型调用**（后者通常
  数百毫秒到数秒）。因此在真实会话里，存储不是瓶颈。
- 重放 0.02 ms/条：1000 条历史恢复只要 22ms，**会话长度不影响恢复体验**。

## 二、长会话（插件反复装卸）

同一插件连续 load/unload N 轮。关心的是**是否线性**——泄漏会表现为超线性增长。

| 轮次 | 实测 | 每轮均摊 |
|---|---|---|
| 1 | 66 ms | 66.1 ms |
| 10 | 50 ms | 5.0 ms |
| 20 | 110 ms | 5.5 ms |

（三次独立运行的数字一致：1 轮 65–67ms，10 轮 47–54ms，20 轮 105–115ms）

**第一轮有约 60ms 的固定开销**（JIT、首次 ALC 加载、首次反射），之后每轮约 5ms。

**线性性验证**：以 20 轮减去预热推算边际成本约 2.3 ms/轮，
预测 20 轮 110ms、实测 110ms（吻合）。

**但 10 轮的预测偏高**（预测 87ms、实测 50ms）。这说明预热不是简单固定值——
10 轮时部分预热成本已被摊薄但尚未完全体现。**这里如实记录不一致，不强行解释。**

**结论**：20 轮没有超线性迹象，与 `KernelRepeatedCycleTests` 的泄漏断言一致。
但轮次再大（50+）未测——需要时再补。

## 三、并发会话（4 会话 × 50 次工具执行）

同一工作区，各会话用**不同资源键**（`file:<ws>/fN.txt`）声明只读操作。

| 项 | 实测 |
|---|---|
| 顺序执行 | 6 ms |
| 并发执行 | 1 ms |
| 加速比 | 6.00× |

**怎么读**：并发确实快于顺序，说明资源级读写键在工作——不同资源的读可以并行。
若锁是"整个工作区一把"，并发会比顺序更慢（上下文切换开销）。

**这组数字的局限**：执行体是空的（只取锁、不放实际 IO），因此测的是
**锁本身的代价**，不是真实工具的性能。绝对数字很小（6ms/200 次），
意义在于"并发不退化"而非"并发有多快"。

**未测**：同一资源键上的争用（那会串行，代价取决于持锁时长）。
真实场景里持锁时间由工具本身决定，基线无法给出通用数字。

## 四、每轮本地开销（2026-10-28 新增）

前面的三项测的是存储、装卸、锁，但**真实会话的时间大头是模型调用**。
这一节补上"我们自己花掉多少"：用零延迟假模型跑完整 `RunAsync`，
剩下的就全是本地开销。

| 历史长度 | 耗时/轮 | 分配/轮 |
|---|---|---|
| 0 条 | 0.02 ms | 4.6 KB |
| 100 条 | 0.02–0.05 ms | 26.5 KB |
| 1000 条 | 0.33–0.48 ms | 223 KB |
| 5000 条 | 0.81–1.09 ms | 1099 KB |

**怎么读**

- 分配随历史**严格线性**增长（约 223 字节/条），来自每轮把 `AgentMessage`
  重新转成 `ChatMessage`。时间观感不高是因为 Gen0 回收极快。
- **真实会话通常 40–300 条消息**（一次 20 轮的工具型对话约 40–60 条）。
  在这个量级上，本地开销 **< 0.1 ms/轮**，而一次模型调用是数百毫秒。
- 5000 条历史 ≈ 1.1 MB 文本 ≈ 30 万 token，已接近或超过多数模型的上下文上限，
  **实际不会达到**。为它优化是给自己找活干。

## 五、工具声明序列化（2026-10-28 新增）

连接器每次构造请求体都要把每个工具的 schema 序列化一次
（`ToolDeclarations.ToSchemaNode` 每次 `JsonNode.Parse`）。

| 工具数 | 耗时/请求 | 分配/请求 |
|---|---|---|
| 4 个 | 0.010–0.032 ms | 5.3 KB |
| 10 个 | 0.020–0.076 ms | 13.3 KB |
| 30 个 | 0.069–0.204 ms | 39.9 KB |

**结论：不值得优化。** 真实场景 4–10 个工具时为 0.01–0.08 ms/请求。
加一层缓存反而引入"schema 变了但缓存没失效"的风险——
而 schema 变化必须让旧审批失效是硬约束（见 `architecture.md` §5.2）。

## 六、token 估算（2026-10-28 新增，已优化）

启用压缩后，**每次模型调用前**都要估算全部历史的 token 数
（`SlidingWindowCompactor.Plan` → `TokenBudget.Estimate`），逐字符判断是否为 CJK。

| 历史长度 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 100 条 | 0.271 ms | 0.099–0.147 ms | −46% ~ −63% |
| 1000 条 | 1.567 ms | 0.701–1.077 ms | −31% ~ −55% |
| 5000 条 | 5.338 ms | 1.964–2.826 ms | −47% ~ −63% |

**做了什么**：加了一条 ASCII 快速路径——整串是 ASCII 时不存在任何 CJK 字符，
用 `Ascii.IsValid`（向量化）一次判定即可跳过逐字符循环。

```csharp
var cjk = 0;
if (!System.Text.Ascii.IsValid(text))
{
    foreach (var character in text)
        if (IsCjk(character)) cjk++;
}
```

**为什么这样安全**：纯 ASCII 时 `cjk` 必为 0，`CjkDiv(0, n)` 返回 0，
与逐字符统计结果**完全相同**。这不是"改小估算值换速度"，
而是"用更快的算法算出同一个数"——`TokenBudget` 那句
"宁可高估也不要低估"的约束没有被触碰。

**等价性验证**：20 组边界输入（null / 空串 / 单字符 / 全角 / 假名 / 韩文 /
代理对 / 各范围边界码位）+ **20 000 组随机输入**，新旧实现输出**零不一致**。

**反证**：把快速路径条件改成恒真（即撤掉优化）后重测，
5000 条历史从 1.96 ms 回到 5.34 ms——差异真实存在，不是测量噪声。

## 七、明确不做优化的地方（2026-10-28）

这一轮把热点都量过了，以下**刻意不动**，理由是数据而非偷懒：

| 项 | 实测代价 | 为什么不优化 |
|---|---|---|
| 每轮重建 `ChatMessage` | 100 条历史 0.02 ms | 真实会话 40–300 条时 < 0.1 ms，占 RoundTrip 的 0.03% |
| 工具 schema 每次重新 parse | 10 个工具 0.02 ms/请求 | 加缓存会引入"schema 变了缓存没失效"的风险，代价大于收益 |
| 存储 `Flush(flushToDisk: true)` | 0.87–4.62 ms/条（噪声大） | **这是提交屏障的成本，不是缺陷**。想更快就得放弃落盘保证 |
| 内核租约下的 `GetToolsAsync` | 含在上面的工具序列化里 | 每轮调用两次是刻意的：第二次用于"避免循环内工具变更导致前后不一致" |

**判据**：优化只在"代价可测且占 RoundTrip 可观比例"时才做。
本轮唯一符合的是 token 估算（5000 条时 5.3 ms，且每次模型调用前都跑）。

## 八、这份基线没覆盖什么

| 未覆盖 | 原因 | 什么时候该补 |
|---|---|---|
| 真实 provider 的端到端延迟 | 依赖网络与模型，不属于本 SDK 的基线 | 已由 M1 的 LiveRun 记录过（含 provider/模型/token） |
| 大量并发会话（>4） | 当前宿主形态是单会话 CLI + 多会话 ACP | 桌面宿主同时开多个会话时 |
| 内存峰值（RSS） | 只测了每轮**分配量**（§四），没测进程峰值 RSS。ALC 回收已由 WeakReference 断言覆盖 | 出现内存相关问题时 |
| 50 轮以上的装卸 | 20 轮已足够暴露线性问题 | 需要长跑验证时 |
| 上下文压缩的耗时 | 一次摘要 = 一次模型调用，延迟由 provider 主导；**决策**部分已测（§六） | 无需单独测 |

## 九、怎么用这些数字

1. **回归对比**：改动涉及存储、生命周期、资源锁或上下文估算时，跑一次 `-- perf` 与本文对比。
   数量级变化（例如追加从 0.72 变成 7 ms/条）需要解释。
   **注意先 `rm -rf spike/.../bin/Release` 重建**——`--no-build` 会用旧 DLL，
   本项目已经因此得到过假结论（2026-10-28 优化时又踩了一次）。
2. **不要拿它做承诺**。对外说"支持长会话"时，依据是"1000 条历史恢复 22ms"
   这个实测，不是"性能很好"这种形容。
3. **换环境要重测**。这份数字绑定上面那张环境表。
