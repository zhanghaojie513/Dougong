# 上下文卫生与记忆优化：三项评估

> **状态**：两项已实现（2026-10-26），一项经评估决定不做。
> **上游**：`docs/skill-l1-acceptance-1.md` 完成后，对照外部实践
> （Hermes/hindsight 的长期记忆设计）审视还缺什么。

---

## 一、做与不做的结论

| 项 | 归属 | 决定 | 理由摘要 |
|---|---|---|---|
| 工具结果进上下文时裁剪 | **可靠性**（不是记忆） | **已做** | 一次 `read_file` 读大文件就能挤爆窗口，是长任务崩溃的直接原因 |
| 压缩时保留最近一次计划 | 上下文 | **已做** | 计划被摘要掉后模型失去"我在做什么"，是目标漂移的典型机制 |
| 记忆产物的取代关系（`SupersedesArtifactId` + 变更原因） | 记忆 | **不做** | L1 只有 3 个白名单键，冲突场景不存在；且是公开类型 + 持久化格式的双重改动 |

## 二、工具结果裁剪（已做）

### 问题

`LoopAgentRuntime.AppendToolExchange` 原本把工具结果**完整原文**放进模型历史，
没有任何上限。唯一的截断在 `ShellTool` 自己（8KB 的 `BoundedBuffer`），
而 `read_file`、MCP 工具都没有。一次读 5MB 文件就够把上下文撑爆。

### 改动

新增 `ToolResultLimits.Clamp`：超过 32K 字符时保留头 24K + 尾 6K，
中间插入显式标记（含省略字符数与原文总长）。

**位置是关键**：只在 `AppendToolExchange` 里裁——那是"即将进入模型上下文"的唯一位置。

| 改动位置 | 后果 |
|---|---|
| dispatcher 出口 | 日志里只有截断内容，**恢复出的会话比原始会话少数据，且无法还原** |
| 日志写入前 | 同上 |
| **拼装模型历史时** | 日志完整、恢复完整、模型看到裁剪版 ✔ |

### 三个不变量

1. 超限结果进上下文时被裁剪
2. 会话日志仍是完整原文（裁剪不是数据丢失）
3. 裁剪通过 `AgentEvent.ToolResultTruncated` 暴露（不能让宿主以为模型看到了全部）

第 3 条不是形式主义：模型看不到标记就会把残缺数据当成完整事实，
那比直接报错更危险。

### 验收

`-- context-hygiene` 8 项。其中 `history-gets-clamped` 与 `store-keeps-full-content`
都走**真实运行时 + 真实 dispatcher**（`ScriptedChatClient` + `FakeTool`）——
只测 `Clamp` 本身是没用的，那样测不出"裁剪压根没接上"。

**反证 5 条**（`scripts/context-hygiene-counterproofs.sh`）全部如期变红，
包括最关键的一条：把裁剪从主路径摘掉（模拟"能力只在测试里"）。

## 三、压缩时保留计划（已做）

### 问题

`SlidingWindowCompactor` 只保留头 2 条 + 尾 6 条，中间全部摘要掉。
模型通过 `todo_write` 写的计划一旦进入中间区间就消失——
它失去了"我要做什么"的显式记录，而摘要未必能概括出足够的任务约束。

### 改动

`TrimToExcludeLatestPlan`：若最近一次计划更新落在待压缩区间内，
把区间末端前移到它之前（并且按工具配对规则回退到发起它的 assistant）。

**只改压缩器，不动 runtime**。这比"每轮把计划重新注入上下文"的破坏性小得多：
- 不改模型输入的结构
- 不碰 `IMemoryInjector` 的语义（记忆开关与计划是两件事）
- 问题本来就是"压缩把它删了"，那就在压缩时别删它

### 为什么只保护计划

不保护所有工具结果——那等于取消压缩。
计划是唯一一类"内容本身就是当前状态、一旦丢失无法从别处重建"的工具结果。

### 验收

`-- compaction` 新增 3 项：计划不被覆盖、保护时工具配对不拆散、无计划时区间不被误伤。
**反证 2 条**如期变红。

## 四、记忆取代关系：为什么不做

外部实践（hindsight）的 observation 是"从多条记忆聚合出的信念，带支撑引文与证据计数"，
新证据到来时**强化、削弱或扩展**，而不是静默替换。

看起来值得学，但对照我们的实际设计，这一项现在做是浪费：

1. **L1 只有 3 个白名单键**（`language` / `output.format` / `naming.convention`），
   取值基本是枚举。用户改主意就是改，不存在"多条证据支持同一信念"的结构。
   hindsight 的强化语义在我们这里是空转。

2. **它是公开类型 + 持久化格式的双重改动**。`MemoryArtifact` 是 `public sealed record`，
   加字段要过 ApiCompat（`init` 属性可避开签名破坏，但仍是公开面变更）；
   `MemoryStore.ParseArtifact` 是手写字段映射，读写两边都要改，
   且旧文件读出来新字段为 null，需要定义 null 语义。

3. **它优化的是一个刚被证明有效的功能**。验收 1 刚跑出 +60%～+90%，
   但"记忆条目怎么合并"在只有三个键的前提下没有实际收益。
   等 L2（行为规则，条目数会上去）才成为真问题。

**如果将来做 L2，这一项应该重新评估**——那时冲突是真问题，
判据也会不同（需要"哪条规则优先"的明确语义，而不只是记一笔变更原因）。

## 五、明确不做的其它项

| 项 | 为什么不做 |
|---|---|
| hindsight 独立记忆服务（PostgreSQL/pgvector） | 我们是嵌入式 SDK，宿主不该被迫跑一个数据库 |
| 图索引（实体/时间/因果） | 需要实体抽取模型 + 一致性维护，与"L1 只存三个白名单键"冲突 |
| 交叉编码器重排 | 需要加载一个模型；依赖面刻意收在 M.E.AI + MCP SDK |
| Mental models 后台重写 | 后台 LLM 调用 = 成本 + 外发，违反"记忆默认关闭、数据流分别可配置" |
| 自动信念强度调整 | 没有评测集就无法判断调得对不对；验收 1 只测了偏好遵循，不测这个 |
| 上下文组装点抽象 | 等真有第二个宿主需求再做，现在抽是猜 |
