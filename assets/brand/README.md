# Dougong 标志使用规范

> 一页纸。够用即止——这份文档的读者是要把 logo 用起来的人，不是设计师。

## 一、标志构成

**合构**：三个直角构件相互咬合——左上角块与下方小方块构成"承托"的立柱，
右侧大块从下方接入并与左上角块上下交叠，缺口处形成一个向右开口的凹槽。

它不是任何具象物的描绘。三个块体**互相穿插而不是并排**，共用一个垂直基准线——
这是"构件逐层叠垒、共同承托"的抽象表达，也是 Dougong 作为 harness 的定位：
**承托而不替代**。

**结构一经确定不再改**：这是 C 修订版，此前三轮（斗拱具象、D 字标、阶梯环）
已被否，理由见 [direction-approved.md](direction-approved.md) 与
内部开发历程。

## 二、颜色

**主标志只有黑白两色**，用纯黑或纯白，不引入任何有彩色。

```
纯黑  #000000     浅色背景上的主标志
纯白  #FFFFFF     深色背景上的主标志
```

**应用图标可以使用灰阶**——这是唯一的例外，见 §四。

> **早期方案曾用琥珀 `#E8A317` 做点缀**，后因"太突兀、与主结构抢注意力"而移除。
> 也试过"玄黑底 + 米白线"的双色方案（阶梯环时期），随结构一并废弃。

## 三、标志文件

| 文件 | 场景 |
|---|---|
| `svg/symbol.svg` | **主用**。纯黑。浅色背景、印刷、PPT、文档插图 |
| `svg/symbol-white.svg` | 纯白。深色背景、深色 App、视频片头 |
| `svg/horizontal.svg` / `-white` | 图标 + 字标的横向组合，用于页眉、README |
| `svg/stacked.svg` | 图标在上、字标在下的纵向组合，用于方形版位 |
| `svg/wordmark.svg` | 只有字标，用于空间极窄处（如页脚署名） |
| `png/symbol.png` / `-white` | 位图版，1024×1024，四角透明 |

**位图只用于无法使用 SVG 的场合**（社交平台头像、即时通讯、旧版 Office）。
能用 SVG 就用 SVG。

## 四、应用图标（唯一允许质感的地方）

`svg/app-icon.svg`、`png/*` 与 `icons/*` 是**应用图标**，不是主标志。
它们可以带石墨灰阶渐变与轻微边缘光，因为要跟系统里其他应用图标并排放。

| 尺寸 | 处理 |
|---|---|
| 16 / 24 / 32 px | 像素校正；石墨纯色底 + 柔白符号；**关闭**渐变、细描边与投影 |
| 48 px | 保留表面与边缘渐变；**关闭**构件投影 |
| 64–1024 px | 完整石墨渐变、柔白构件、细边缘光与轻微阴影 |

```
icons/dougong-{16,24,32,48,64,128,256,512,1024}.png
icons/dougong.ico        含前七个尺寸的多帧 ICO，Windows 桌面直接用这个
png/app-icon-light.png   反色版：浅灰底 + 深色构件
```

灰阶全部 R=G=B，光照方向统一从左上到右下。

**应用图标的质感版不用于印刷、刺绣或纯单色界面按钮**——那些场合用 §三 的
主标志，纯黑白、无渐变。

## 五、最小尺寸

| 场景 | 最小尺寸 |
|---|---|
| 屏幕 | 16px |
| 印刷 | 8mm |

16px 使用 `icons/dougong-16.png`（已做像素校正）。
**低于 16px 不要使用**，块体间隙会闭合。

## 六、安全区

标志四周留白至少等于**最大块体边长的 1/4**（约标志边长的 1/8）。

```
┌─────────────────────┐
│   ┌───────────┐     │
│   │           │     │  ← 留白 ≥ 1/8 边长
│   │   标志     │     │
│   └───────────┘     │
└─────────────────────┘
```

## 七、禁止的用法

| 禁止 | 原因 |
|---|---|
| 旋转 | 三个块的承托关系有方向，转了就断了 |
| 拉伸变形 | 块体必须是正方形，比例是识别度的来源 |
| 改变块体间距 | 咬合处的间隙决定它像"合构"还是像随机色块 |
| 给主标志加投影、发光、描边 | 主标志是纯黑白；质感只属于应用图标 |
| 主标志上用其他颜色 | 见 §二 |
| 把应用图标的渐变拿去印刷 | 见 §四 末段 |
| 缩小到 16px 以下 | 见 §五 |

## 八、与文字的组合

`svg/horizontal.svg` 与 `svg/stacked.svg` 已包含**转成路径**的字标，
不依赖机器字体，可放心用于任何环境。

**自己排版时**（例如需要动态改变字号）：

```css
.brand-wordmark {
  font-family: -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif;
  font-weight: 600;
  letter-spacing: -0.02em;
  font-size: 1em;           /* 相对图标高度的 0.45 倍 */
  text-transform: lowercase; /* 一律小写 */
}
```

**已实测的最佳组合**：

```
图标 128px  +  dougong  semibold 62px  -0.02em  lowercase
间距        图标右边到文字左边 = 36px（图标宽度的 28%）
垂直对齐    文字的 x-height 中心 对齐 图标中心
```

**为什么一律小写**：小写的 `dougong` 有多个圆形字腔（o、g），与图标的
直角块体形成张力；全大写会变成一堵墙，压过图形。

## 十、这个目录曾被整体替换

2026-10-29 之前这里是**阶梯环**方案（玄黑底 + 米白线，六个尺寸变体，
立体桌面图标）。用户确认改用黑白质感版的"合构"结构后，
旧素材完整归档在 `docs/brand-archive/stepped-ring/`，
不参与构建，只供追溯。

**为什么留着而不是删掉**：logo 换了四轮，每一轮的理由都记在
内部开发历程。删掉旧图会让"当时为什么否掉那个方向"变成无法复核的口头说法。

## 十一、什么没做

| 项 | 状态 |
|---|---|
| 商标检索 | **未做**。正式启用前应做反向图片搜索与商标库检索 |

## 十二、终端呈现

CLI 在真终端里运行时的视觉规格。**档位不是"好看/一般/难看"，
是"能显示什么"的客观分流**。

### 12.1 三档分流

| 档 | 触发条件 | 颜色与符号 | 底部状态行 |
|---|---|---|---|
| Rich | 交互 && 宽 ≥ 80 | 有 | 有（底部锚定） |
| Narrow | 交互 && 60 ≤ 宽 < 80 | 有 | 有（画在光标下方） |
| Plain | 重定向 \|\| 宽 < 60 | 无 | 无 |

**Plain 档是与改造前逐字节相同的**。这不是"降级体验"，是"信息编码开关"：
Rich/Narrow 档多出来的只有颜色与符号，文本内容本身各档完全一致。

**启动时清屏**（`ESC[2J ESC[H`）：只在 Rich/Narrow 且未重定向时执行。
Plain 档多一个控制字符就是破坏——46 个自检套件断言逐字文本。

**不用备用缓冲区**（`ESC[?1049h`）：那会让历史不进 scrollback、退出后整屏消失、
SSH/终端复用器下更脆。Hermes 自己在 Termux 上就关掉了全屏，理由相同。

### 12.2 首页：云拱字符画，四档

| 档 | 触发 | 内容 |
|---|---|---|
| full | 宽 ≥ 66 且高 ≥ 24 | 30×18 形象 + 右侧信息并排 |
| stacked | 宽 46–65 且高 ≥ 24 | 形象在上、文字在下 |
| compact | 宽 ≥ 46 | 20×12 形象 |
| ascii | 宽 ≥ 34 | 纯 ASCII 24×14 |
| text | 其余 | 单行标题 |

字符画来自 `artifacts/brand-character/yungong-refined/text/`，
由 `scripts/gen-yungong-art.py` 生成到 `src/Dougong.Cli/Terminal/YungongArt.cs`。
**不手抄**——手抄一次就会和源文件漂移，而终端图形本来就不好对账。

**高度要求不是随手写的**：18 行形象 + 3 行信息 + 状态行 + 提示符，
24 行刚好放下；20 行终端放不下，必须降档否则底部被挤出屏幕。

**高度未知（0）时按"放得下"处理**：那说明终端不报高度，而宽度已经证明
它是真终端。给完整形象最多挤一点，降档则是白丢信息。

**字符画不补右侧空格**：源文件各行 17–30 不齐，补齐会变成实心矩形，
右侧一堵空白墙。

### 12.3 颜色

**默认黑白灰**。这是两份文档冲突后的裁决：
`artifacts/brand-character/yungong-refined/设计理念.md` §后续视觉约束
（2026-10-30）写"终端默认保持黑白灰，**不因神话参照引入黄金配色**"，
晚于本节早先"用金色做强调色"的写法，以它为准。

```
            默认 (mono)   朱构 (zhugou)   用途
Accent      #E8E8E8       #C0392B        版本号、模型名、提示符、字符画
Muted       #7A7A7A       #7A7A7A        路径、耗时、次要说明
Ok          #4CAF50       #4CAF50        ✓ 成功
Warn        #FF8C00       #FF8C00        ⚠ 警告
Error       #EF5350       #EF5350        ✗ 失败
```

**语义色不随主题变**：`Ok`/`Warn`/`Error` 是信息编码，"红=错误"是全终端世界的
共识，不该为了配色统一去动它。

**黑白灰之后 accent 只剩"亮/暗"一档**，所以只能用在**小面积**
（spinner 一帧、提示符、字符画）。用亮白刷大面积文本会让整屏发灰、失去层次。

主题由 `DOUGONG_THEME=mono|zhugou` 选，默认 `mono`；`/status` 里显示生效值。

### 12.4 底部状态行

**一行，忙闲共用同一个槽位**——这是 Hermes 的结构
（`appChrome.tsx:735-745`：忙时 `FaceTicker`，闲时静态文案）。

```
◇ │ mimo-v2.6-flash │ 12.0K/1.0M ██░░░░░░░░ 1% │ 4.2s        ← 空闲
| (¬‿¬) 思考中… │ mimo-v2.6-flash │ 12.0K/1.0M ██░░░░░░░░ 1% │ 3s   ← 忙
> _                                                          ← 提示符
```

**状态行在提示符上方**，方向与 Hermes 一致（`appLayout.tsx:420` 的
StatusRulePane 在 `:424` 输入 Box 之前）。为此提示符由底部区域自己画，
不再是正文。

**空闲时也常驻**，不消失。`ui.statusBar` 默认 `'top'`，只有显式配 `'off'` 才关。

**启动即画出**：状态行只有两个触发点（泵线程、轮次结束），而启动到首次提问
之间没有轮次——所以挂载区域后立刻调一次 `ShowIdle()`。

**渐进披露**：左段（指示符 / 模型名）不可压缩、先占位；尾部段
（上下文 / 耗时）按序逐个 `fits()` 尝试，**放不下的整段丢弃，不截断中间**。
窄终端把上下文压成 `12K tok` 并去掉进度条——模型名比进度条精度重要。

**还没调用过模型时显示 `≤1.0M`（窗口容量）而不是整段消失**：
用户第一件想确认的事是"这个模型能装多少"。不报 `0%`——
那会让人以为已经用了一点，而实际是一次请求都没发。

- spinner 用 ASCII `| / - \`，250ms 一帧——任何终端都不会错位
- 面孔每 2500ms 换一次；250ms 换表情会晕
- 进度条用 `█`/`░`，**不用方块 emoji**：后者在部分终端占两格，整行会错位

### 12.5 已知限制

- **没有滚动重锚**：正文写满最后一行时终端整体上滚，而锚定区域按绝对行号
  定位。真机未观察到错位，但这是一处未处理的技术债。
- **没有 raw mode 输入层**：光标移动、历史、补全、多行编辑都没有。
  这是 Hermes 的 `TextInput`（1570 行）级别的工程，不在本次范围内。
  **视觉可以对齐，交互不能。**
- **窗口 resize 不重排**：只在启动时读一次尺寸，`/status` 里如实显示。
